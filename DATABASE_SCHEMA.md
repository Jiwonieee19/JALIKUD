# Jalikud PostgreSQL Database Schema

## Scope

This is a documentation-only proposal for the Jalikud database. It does not
create a database, connect PostgreSQL, or add migrations, models, API routes,
seed data, frontend code, or backend code.

The schema reflects the current mobile screens: accounts, branches, addresses,
menu products, customization, deals, vouchers, carts, orders, and rewards.

## PostgreSQL conventions

- Primary keys: `bigint GENERATED BY DEFAULT AS IDENTITY`
- Money: `numeric(12,2)`
- Date/time: `timestamptz`
- Currency: ISO 4217 `char(3)`, default `PHP`
- Names: lowercase `snake_case`
- Every foreign key should have an index unless an existing composite index
  already starts with that column.

## Relationship overview

```text
users ──< user_addresses
  ├──── default_branch_id >── branches ──< branch_products >── products
  ├──< carts ──< cart_items ──< cart_item_add_ons
  ├──< orders ──< order_items ──< order_item_add_ons
  │       ├──< order_status_history
  │       └──< voucher_redemptions >── vouchers
  ├──< reward_redemptions >── rewards
  └──< reward_point_transactions

categories ──< products ──< product_variants
                         └──< product_add_ons >── add_ons
deals ──< deal_items >── products
```

- `products (category_id, is_active)`
- `branch_products (branch_id, is_available)`
- `deals (is_active, starts_at, ends_at)`
- `carts (user_id, status)`

- `cart_items (cart_id)`
- `orders (user_id, status, created_at DESC)`
- `orders (branch_id, status, created_at)`
- `order_items (order_id)`
- `order_status_history (order_id, created_at)`
- `voucher_redemptions (voucher_id, user_id)`
- `reward_redemptions (user_id, status)`
- `reward_point_transactions (user_id, created_at)`

Add PostgreSQL full-text or trigram indexing to `products.name` later if catalog
search volume requires it.

## Integrity and transaction rules

1. Checkout should be one transaction: validate prices and voucher, create the
   order and item snapshots, record voucher use, convert the cart, and commit.
2. Product and deal prices must be validated server-side. Client totals are not
   authoritative.
3. Historical orders should not be hard-deleted. Deactivate catalog records
   instead of deleting data required for audits.
4. Voucher limits require row locking or another concurrency-safe approach.
5. Reward redemption must safely lock/validate the points balance to prevent
   concurrent overspending.
6. Store only password hashes and payment-provider references. Never store raw
   passwords, biometric data, or full card details.
